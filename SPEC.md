# SPEC — устройство интернет-магазина

Версия 0.1 · 20 октября 2026 · Статус: черновик технической спецификации

Документ описывает способ реализации требований из `PRD.md`. Если библиотека или сервис обновились, кодовый агент сверяет точные команды и API с официальной документацией перед изменением кода.

## 1. Предлагаемая основа

| Область | Выбор |
|---|---|
| Сайт и сервер | Next.js App Router, React, TypeScript |
| Оформление | Tailwind CSS с собственными токенами и компонентами магазина |
| База данных | PostgreSQL в Neon |
| Доступ к базе | Drizzle ORM и официальный Neon Serverless Driver |
| Аккаунты | Better Auth: email/пароль и Google OAuth |
| Проверка входных данных | Zod на серверной границе |
| Медиа | S3-совместимое объектное хранилище; точного поставщика выбрать до этапа загрузки фото |
| Оплата, поздний этап | ЮKassa, отдельный тестовый магазин |
| Автоматические проверки | Vitest для логики и Playwright для ключевых путей в браузере |
| Развёртывание | Vercel для сайта и Neon для базы; регион выбрать по доступности проекта и задержке для Узбекистана |

Устанавливаются только зависимости, нужные конкретной задаче. Точные версии фиксируются в `package-lock.json`. Не хранить OAuth-секреты, пароль базы и ключи ЮKassa в Git или публичных переменных браузера.

## 2. Схема приложения

```text
Браузер покупателя / администратора
                │ HTTPS
                ▼
     Next.js: страницы и действия
       ├── Better Auth ── Google OAuth
       ├── слой доступа к данным
       │        └── Drizzle ── Neon PostgreSQL
       ├── медиа-адаптер ── S3-хранилище
       └── обработчик уведомлений ── ЮKassa TEST (этап оплаты)
```

Страницы и серверные действия обращаются к одному слою доступа к данным. Клиент не подключается к базе напрямую. Критичные операции — создание заказа, изменение остатка, роли и статуса оплаты — выполняются на сервере.

## 3. Основные данные

Better Auth хранит собственные записи пользователя, сессии и связки OAuth. Таблицы магазина ссылаются на внутренний ID пользователя.

| Таблица | Для чего нужна |
|---|---|
| `profiles` | Имя, телефон и ключ фотографии пользователя |
| `categories` | Дерево разделов каталога и адреса страниц |
| `brands` | Названия производителей |
| `products` | Артикул, название, категория, бренд, цена UZS, остаток, статус публикации и характеристики |
| `product_media` | Порядок фотографий, подпись и ключ объекта в хранилище |
| `user_roles` | Отдельное назначение `customer` или `admin` |
| `addresses` | Адреса доставки, принадлежащие одному пользователю |
| `cart_items` | Текущая корзина: пользователь, товар и количество |
| `favorites` | Сохранённые товары пользователя |
| `orders` | Пользователь, адрес-снимок, сумма, этап обработки и статус оплаты |
| `order_items` | Снимки товара, цены, количества и суммы в заказе |
| `payments` | ID платежа провайдера, сумма, валюта и проверенный статус |
| `admin_audit_logs` | Кто, когда и какое важное изменение сделал в админке |
| `telegram_links` | Проверенная связь `telegram_user_id` с `profiles.user_id` и статусом подтверждения |

Денежные суммы магазина хранятся целыми числами в UZS. Товар в уже созданном заказе не меняется при последующем редактировании каталога. Статус оплаты и этап доставки — отдельные поля.

## 4. Страницы и доступ

| Адрес | Доступ | Назначение |
|---|---|---|
| `/` | Все | Промо, крупные категории и товары |
| `/catalog/[slug]` | Все | Категория, фильтры, сортировка и страницы товаров |
| `/product/[slug]` | Все | Фото, цена, характеристики и наличие товара |
| `/search` | Все | Результаты поиска |
| `/cart` | Все | Гостевая или аккаунтная корзина |
| `/account/sign-in`, `/account/register` | Все | Вход email/пароль и Google, регистрация |
| `/account/profile`, `/account/settings` | Покупатель | Контакты, пароль, фото профиля и ссылки на покупки |
| `/account/orders` | Покупатель | Только свои заказы и их детали |
| `/checkout` | Покупатель | Проверка адреса и корзины перед созданием заказа |
| `/admin/**` | Только администратор | Каталог, остатки и этапы обработки заказов |

Проверка роли на сервере обязательна и для страницы, и для каждого изменяющего действия. Скрытая кнопка или проверка только в браузере доступ не защищает.

## 5. Регистрация и профиль

- Better Auth обслуживает email/пароль, сессию и Google OAuth; пароль не записывается в собственную таблицу магазина.
- Для Google задаются отдельные разрешённые callback-адреса разработки и опубликованного сайта. `clientSecret` остаётся только на сервере.
- Сессия хранится в cookie с `HttpOnly`, `Secure` на HTTPS и `SameSite` согласно настройке выбранной версии Better Auth.
- Профиль и настройки доступны после входа. В каждом запросе сервер берёт ID пользователя из проверенной сессии, а не из поля формы.
- При отсутствии фото профиль показывает заглушку. Для загрузки принимаются JPEG, PNG или WebP с ограничением размера; сервер проверяет реальный формат файла и имя, а не только расширение.
- В `profiles` хранится ключ изображения, а не произвольный URL от клиента. Фото можно заменить или удалить.
- Смена и восстановление пароля выполняются через документированный механизм Better Auth; приложение не реализует криптографию паролей самостоятельно.

## 6. Каталог, поиск и изображения

- Сначала создаются 6 стартовых категорий и около 30 mock-позиций для заполнения каталога. Карточки и цены MediaPark не копируются.
- `price_uzs` и остаток проверяются ограничениями базы; выключенный товар не появляется в публичном каталоге.
- Сервер поиска принимает ограниченную строку, фильтры, сортировку и номер страницы. В URL остаются выбранные фильтры.
- Изображения сохраняются под непредсказуемым именем. Каталожные изображения доступны для чтения; загрузка и удаление разрешены только администратору.
- До подключения хранилища интерфейс использует локальную заглушку, чтобы отсутствие внешнего сервиса не ломало карточку.

## 7. Корзина и оформление

- Гость может хранить корзину в браузере только как список ID товара и количества. Сервер всё равно заново читает действующие цены и наличие.
- После входа сервер объединяет гостевые позиции с аккаунтной корзиной по ID товара, применяет лимит количества и не принимает от клиента цену.
- Создание заказа выполняется в транзакции: сервер проверяет наличие, записывает сумму и товарные снимки, резервирует/уменьшает остаток по согласованным правилам.
- Заказ хранит снимок адреса и товаров, чтобы история не зависела от последующих правок профиля и каталога.
- Повторный запрос создания заказа не создаёт второй заказ. Для этой операции задаётся ключ идемпотентности.

## 8. Администрирование

- Назначать `admin` можно только через защищённую операцию или управляемую процедуру первоначального развёртывания.
- Администратор может публиковать и скрывать товар, менять цену и наличие, а также этап обработки заказа.
- Администратор не может вручную выставить `paid`. Оплата появляется только после подтверждённого события провайдера.
- В журнале действий не сохраняются секреты, пароль, полный OAuth-токен или данные карты.
- Товар с историей заказов скрывают из продажи; его не удаляют так, чтобы сломалась история.

## 9. ЮKassa — отдельный тестовый этап

На этапах до оплаты отображается только экран будущей оплаты; он не создаёт видимость списания денег. Перед интеграцией кодовый агент сверяет аккаунт и действующие настройки тестового магазина с актуальными документами ЮKassa.

1. Сервер пересчитывает сумму по текущему заказу и создаёт платёж у ЮKassa с ключом идемпотентности.
2. Покупатель переходит на размещённую ЮKassa страницу подтверждения. Магазин не собирает номер карты и CVC.
3. Возврат покупателя на сайт не меняет `payment_status` на оплаченный.
4. Уведомление служит сигналом: сервер получает актуальное состояние платежа из API, проверяет ID заказа, сумму и валюту, затем однократно фиксирует результат.
5. Тестовые ключи и endpoint отделены от коммерческих настроек. Переключение на реальные ключи на этом этапе недоступно.
6. Каталог всегда показывает цену в UZS. Примеры API ЮKassa используют RUB, поэтому до разработки надо подтвердить валюту, доступную в конкретном тестовом магазине. Нельзя молча конвертировать сумму; если тестовому магазину нужна конвертация, курс и сумма показываются покупателю и сохраняются вместе с заказом.
7. Тестовый `succeeded` не запускает настоящую отгрузку. Заказ остаётся помеченным как тестовый.

## 10. Проверки и ошибки

- Модульные проверки покрывают фильтры каталога, расчёт корзины, валидацию формы, смену этапов заказа и дубли платежных уведомлений.
- Интеграционные проверки покрывают вход и разграничение доступа к профилю, корзине и заказу.
- Браузерный сценарий проходит путь от каталога до истории заказа на desktop и mobile viewport.
- Проверяются невалидная форма, пустой поиск, отсутствующая фотография, пустая корзина, отказ Google OAuth и повтор webhook.
- Ошибка внешнего сервиса объясняется пользователю; сервер не раскрывает ключ, SQL или внутреннюю трассировку.
- Сборка, TypeScript и lint проходят перед закрытием крупного этапа разработки.

## 11. Telegram Mini App и общие API

- Точка входа Mini App расположена по адресу `/tg` (и поддерживает работу на всех пользовательских маршрутах `/catalog`, `/search`, `/product/[slug]`, `/cart`, `/checkout`, `/account/orders` внутри контейнера Telegram WebApp).
- Токен бота `TELEGRAM_BOT_TOKEN` хранится исключительно в серверных переменных окружения (`.env.local`) и никогда не передаётся в браузер. Публичными могут быть только `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` и `NEXT_PUBLIC_TELEGRAM_MINI_APP_URL`.
- Сервер проверяет `initData` на маршруте `POST /api/telegram/auth` по алгоритму Telegram WebApp (`HMAC-SHA256` с ключом `HMAC_SHA256("WebAppData", TELEGRAM_BOT_TOKEN)` и проверкой `auth_date`). Для локальной разработки без живого контейнера Telegram допускается явный dev-режим проверки только при `NODE_ENV !== "production"`.
- Привязка Telegram-аккаунта к существующему профилю магазина выполняется через `POST /api/telegram/link` только после явного действия пользователя (подтверждение связки в интерфейсе). Молчаливое объединение аккаунтов не допускается.
- Каталог (`GET /api/catalog`), корзина (`GET/PUT /api/cart`) и заказы (`GET/POST /api/orders`) работают через серверные маршруты Next.js, читают актуальные цены из Neon PostgreSQL и используют ключ идемпотентности `idempotencyKey` при оформлении заказа, чтобы повторное нажатие кнопки в Mini App или при нестабильной сети не создавало дубликат заказа.

### Правила проверки доступа к общим серверным API (`DB-09`)

| Маршрут API | Доступ | Правило серверной проверки |
|---|---|---|
| `GET /api/catalog` | Публичный | Возвращает только опубликованные товары (`is_published = true`) и актуальные цены в UZS из БД |
| `POST /api/auth/register`, `POST /api/auth/sign-in`, `POST /api/auth/password-reset`, `POST /api/auth/google`, `GET/DELETE /api/auth/session` | Публичный / Сессия | Пароли хешируются через `scrypt`; сессия хранится в `HttpOnly` cookie (`em_session`) или передаётся через `Authorization: Bearer` |
| `GET/PATCH /api/account/profile`, `POST/DELETE /api/account/avatar`, `GET/POST /api/account/addresses` | Только владелец | `userId` определяется строго из проверенной серверной сессии (`getSessionUser`); аватары проверяются по магическим байтам (`JPEG`, `PNG`, `WebP`) и размеру `<= 2 МБ` |
| `GET/PUT /api/cart` | Гость / Покупатель | При наличии сессии запрещено чтение/запись чужой корзины (`403`); количество ограничено `1..9`, цены подставляются сервером из каталога |
| `GET/POST /api/orders` | Покупатель | `GET` возвращает только заказы владельца (`403` при запросе чужого email); `POST` проверяет наличие, сохраняет снимки товаров/цен и защищает от повторов по `idempotencyKey` |
| `GET/POST/PATCH /api/admin/products`, `GET/PATCH /api/admin/orders` | Только `admin` | На каждом запросе проверяется `sessionUser.role === 'admin'`; ручное выставление `paymentStatus = 'paid'` запрещено (`400`); все изменения пишутся в `admin_audit_logs` |
| `POST /api/payments/yookassa/create`, `POST /api/payments/yookassa/webhook` | Тестовый контур ЮKassa (`TEST`) | Боевые ключи `live_*` отклоняются (`403`); webhook сверяет `providerPaymentId`, `orderId`, сумму и валюту и однократно фиксирует `paid` |
